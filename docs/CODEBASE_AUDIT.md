## Boundaries and the actual cause of cycles

`dependency-cruiser` finds 13 cyclic paths around outfit generation:

1. `outfit-engine.ts` ↔ `outfit-accessories.ts` (the engine calls the belt selector, which imports `fold` from the engine).
2. `outfit-scoring.ts` ↔ `outfit-accessories.ts` (scoring uses `beltEvidence`, while the accessories module uses `Decision`/`styleFamily`).
3. `outfit-scoring.ts` ↔ `outfit-shoes.ts` (scoring uses footwear decisions, while footwear imports a scoring helper).
4. Additional paths between colors, accessories, and the engine pass through these dependencies.
5. Importing the `Garment` type from `./index.js` in `accessories.ts` and `outfit-*` loops through the barrel that exports those same modules. This expands the graph and obscures dependency direction.

First move canonical types and small neutral helpers outside the barrel, replace internal barrel imports with direct imports, and establish one-way flow: domain/types → pure rules → scoring → composition. Generator tests must determine whether `beltEvidence`/`shoeDecision` remain separate decisions or are supplied as scoring data.

## Flows and risks confirmed in code

- Web is an SPA: `main.tsx` creates Router/QueryClient and defines routes; feature views call the shared `api.ts` client; the API is a BFF.
- `apps/api/src/app.ts` concentrates data access and routing. Many handlers compose Supabase queries directly, with validation and auth in the same module. Changes need contract tests for statuses, schemas, and owner/wardrobe authorization.
- Worker `index.ts` registers wardrobe/image jobs, the Gemini queue, and outbox dispatch. `pipeline.ts` and `mask.ts` are already extracted; protect their contracts with real-image fixtures without overwriting originals.
- `garments.tsx` contains detail/form views, inline-edit coordination, custom fields, rotation debounce, suggestions, processing status, and outfit sections; detail navigation and query invalidation must remain consistent during extraction.
- `other-pages.tsx` contains many non-garment views, risking Settings/Gemini, queue control, outfit, laundry, and family regressions during apparently unrelated changes.
- `styles.css` has 3996 lines; changing it without screenshot baselines poses a high visual risk.
- Knip identifies `GarmentCard`, `UPLOAD_CONCURRENCY`, `callGemini`, `neutralColor`, types, and dependencies. Do not automatically treat them as dead code: some are test exports or extraction leftovers.

## E2E coverage and missing evidence

- Mocked `garment-detail-ux.spec.ts`, `gemini-settings.spec.ts`, and `style-profile.spec.ts` passed 6/6 on desktop/mobile. They intercept `/api/**`, so they verify UI interactions rather than live backend integration.
- The current `tests/e2e/wardrobe.spec.ts` E2E test registers and signs in, creates a wardrobe, and uploads a PWA icon. It neither cleans up nor validates a real garment image, and was not run against the existing environment.
- `garment-detail-ux.spec.ts`, `gemini-settings.spec.ts`, and `style-profile.spec.ts` intercept `/api/**`, testing UI/contracts against mocks rather than running API/database services.
- A safe ephemeral E2E tenant lifecycle is missing: fixture user with guaranteed `finally` cleanup, isolated Storage prefix, reset limited to the fixture user, and a separate test for a dedicated non-production database.
- There is no automated visual comparison against approved screenshots. The screenshot helper saves images but is not a pixel-diff/regression gate.
- Risk areas needing stronger tests before refactoring: API sessions/CSRF, two-user RLS, custom properties, batch partial failure/retry, rotation persistence and reprocessing idempotency, AI overwrite conflicts, Gemini limiter fairness/cancellation/retry, saved outfit descriptions, and real Storage cleanup.

## Audit conclusion

The scope does not justify mechanically rewriting all 12k lines. Priorities are (1) contract tests and isolated E2E, (2) splitting `garments.tsx`, `other-pages.tsx`, `context.tsx`, (3) API route/service/data-access separation around `app.ts`, (4) one-way shared dependencies and removal of 13 cycles, (5) separating worker dispatch from handlers, and (6) reducing typed lint debt per module before updating baselines. The detailed plan/status for all modules is in `docs/REFACTOR_PLAN.md`.
